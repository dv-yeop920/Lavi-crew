# 007. Zod 기반 폼 검증과 오류 계약

- 상태: Accepted
- 날짜: 2026-07-24

## 배경

인증·프로필·관리 폼이 각각 수동 문자열 검사와 `null` 반환을 사용해 사용자가 어떤 입력을
수정해야 하는지 알기 어려웠다. HTML 기본 검증만으로는 Server Action을 직접 호출하는 요청을
신뢰할 수 없고, Supabase Auth 및 PostgreSQL 오류 원문을 그대로 노출해서도 안 된다.

## 결정

- 입력값이 있는 모든 폼은 기능 `schemas` 디렉터리의 Zod 스키마를 단일 서버 검증 기준으로 쓴다.
- Server Action은 `safeParse` 성공 데이터만 Controller로 전달한다.
- 검증 실패는 `FormActionResult`의 `fieldErrors`와 사용자 안전한 `message`로 반환한다.
- 필드 오류는 공통 `TextField`의 오류 슬롯과 Semantic `negative` 색상을 사용한다.
- 비밀번호는 앞뒤 공백을 임의로 제거하지 않는다.
- Supabase Auth와 PostgreSQL 오류는 Controller의 명시적 매퍼를 거쳐 사용자 행동으로 복구할 수
  있는 문구로 바꾼다. 중복 가입처럼 계정 열거 위험이 있는 경우 존재 여부를 확정적으로 말하지
  않는다.
- 식별자만 전달하는 삭제·중지 액션도 Zod UUID 스키마로 검증한다. 입력값이 없는 로그아웃·확인
  폼은 별도 값 검증 대상에서 제외한다.
- 실패한 Server Action 폼은 제출 직전 값을 브라우저 안에서만 보관한다. 응답의 `fieldErrors`에
  포함된 입력만 비우고 나머지 입력은 복원하며, 비밀번호 같은 민감값을 서버 응답에 다시 포함하지
  않는다.

## 결과

- 필드별 문구와 접근성 연결을 모든 폼에서 같은 방식으로 재사용할 수 있다.
- View, Action, Controller의 책임이 명확해지고 검증 전 데이터가 서버 유스케이스로 전달되지 않는다.
- Zod가 클라이언트 번들에 포함되지 않도록 View는 공통 오류 타입과 표시 헬퍼만 사용한다.
